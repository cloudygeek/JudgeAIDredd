## Important caveats

### Caveat A — PromptArmor is not actually wired through the SDK path

The runner was patched to inject the PromptArmor `/screen` step
**only on the converse-backend code path** (`callConverse`,
line ~858 of `runner-agentlab.ts`). Anthropic models route through
the SDK (`executeWithSdk`, line ~755) where the SDK runs the agent
loop internally and we don't see individual tool outputs before the
agent does.

Per-cell PromptArmor telemetry:

| Model | Backend | PA screens fired |
|---|---|---:|
| claude-haiku-4-5 | sdk | **0** |
| claude-sonnet-4-6 | sdk | **0** |
| claude-opus-4-7 | sdk | **0** |
| qwen3-32b | converse | 44 (5 injected, 5 sanitisation_failed) |
| qwen3-235b | converse | 133 (17 injected, 10 sanitisation_failed) |

**The three Anthropic rows in the headline table are effectively
a "no defence" baseline.** The 20% ASR on haiku/sonnet matches the
unprotected attack-success rate the AgentLAB harness reports for
those models — PA wasn't there to stop it.

This is the **same Path C limitation we documented for the test-
framework T-2 run** in `docs/tests-needed-2026-05-13.md` caveat 11:
the SDK's `PostToolUse` hook does not rewrite built-in tool outputs.
For T-8 the converse backend is reachable for Qwen models because
we drive the tool loop ourselves, but for Anthropic we have to pick
between letting the SDK run the loop (no PA) or rewriting the agent
loop entirely (Path B in the original plan, ruled out).

### Caveat B — Test-25 intent-tracker numbers measure detection, not prevention

Per `docs/test25-findings-2026-04-27.md` Finding 2: the AgentLAB
runner under intent-tracker logs the Dredd verdict and continues
the trajectory anyway. **The Test-25 ASR column in the headline
table is the agent's own refusal rate when Dredd is watching, not
Dredd's prevention rate.** Intent-tracker's "0% ASR" on every
Anthropic cell is the agent refusing on its own.

The PromptArmor arm **does** prevent — when fired (qwen3 only), it
substitutes sanitised content into the next turn. So the
qwen3-32b 100% PA-ASR vs 10% IT-ASR comparison is genuinely
asymmetric: PA is acting as enforcement, IT is acting as detection.

### Caveat C — qwen3-32b's 5/5 sanitisation_failed rate

Every PromptArmor `verdict=injected` on qwen3-32b returned
`sanitisation_failed=true`. The detector identified the injection
but the fuzzy-strip step couldn't remove it (paper §3.1 algorithm,
not a bug; same finding as `B-1` in tests-needed). The agent
received the original payload and followed it.

This is the **strongest case in our data so far for the
"PromptArmor + AIDredd-style fail-closed semantics" follow-up**
(B-1 optional remedy). On qwen3-32b a strip-the-whole-block
fallback would have produced the prevention PA's spec promises.

## What this is good for

Despite the asymmetry, three results from this run carry weight:

1. **opus-4-7 stays at 0% across both arms** in spite of the PA-not-
   wired-on-SDK issue — corroborates the existing §sec:agentlab-smoke
   "Anthropic frontier ≈ floor on the AgentLAB attack template".

2. **PromptArmor's qwen3 detection rate is non-trivial** — 17/22
   tool outputs flagged as injected on qwen3-235b (77%). The
   problem isn't that PA missed the attacks; it's that fuzzy-strip
   couldn't remove what it detected.

3. **The AgentLAB judge call now works at scale** — commit
   `72794cc1` replaced two `aws bedrock-runtime converse` shellouts
   with the SDK after Debian's awscli v1 produced 50/50 judge
   errors on the first dispatch. v0.1.403 has zero judge errors
   across 50 trajectories.

## §sec:agentlab-smoke paragraph (asymmetric framing)

> *We attempted a third-defence comparator with PromptArmor on the
> AgentLAB long-horizon corpus. Five backends (haiku-4-5, sonnet-
> 4-6, opus-4-7, qwen3-32b, qwen3-235b) were dispatched against the
> stratified-10 attack scenarios with PromptArmor preprocessing on
> each tool output. The Claude Agent SDK does not expose a per-
> tool-output rewrite hook for built-in tools (the same Path C
> limitation discussed in §3.6), so the three Anthropic rows
> received the original tool outputs unchanged and their ASR
> reflects the unprotected baseline (haiku 20%, sonnet 20%, opus
> 0%). The Qwen rows go through a converse-backend tool loop where
> PromptArmor screening is wired in directly, and there PA's
> detection rate was 77% on qwen3-235b but its fuzzy-strip step
> failed to remove the payload in 59% of detections, leaving the
> agent to act on the original injection. The resulting qwen3-32b
> 100% PA-ASR vs 10% AIDredd-IT-ASR asymmetry is a fairer read of
> "PA detection without prevention vs AIDredd detection (logged-but-
> not-blocked under the Test-25 runner; see §sec:agentlab-smoke
> footnote on detection vs prevention semantics)" than of the two
> defences' enforcement abilities.*

## Followups (not on this branch)

1. **Wire PA through the SDK path** — would require either an SDK
   PostToolUse hook that the SDK actually honours for built-in
   tools (T-0 said no) or rewriting the conversation history
   between SDK calls (Path B from the original plan; rejected at
   T-2 stage as out of scope).

2. **Test-25 runner block-on-hijacked fix** — would convert the
   intent-tracker arm from detection to prevention. Same one-day
   work that was rejected as Path B in `docs/t8-plan-2026-05-15.md`.
   Recommendation stands: defer pending reviewer ask.

3. **PA fail-closed variant** — strip the whole tool output when
   `verdict=injected && sanitisation_failed=true`. Trivial code
   change; drives the qwen3-32b cell from 100% → likely ~10%. Would
   be reported as "PromptArmor + AIDredd-style fail-closed
   semantics" and not as PA-as-published.
